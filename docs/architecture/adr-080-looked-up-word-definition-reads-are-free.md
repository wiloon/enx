# ADR-080：查过的词读释义不扣每日查词配额

ADR-079 让 QUERY 按请求里的词数扣每日查词配额，预取也一样。实现预取时（PR #823）发现，这会把配额花在用户没点的词上：e2e 的测试用户按默认免费档 200，刷几次页面配额就被预取用光，之后的点击查词收到 429。真实用户也一样：每篇新文章里有高亮、本地没缓存的词都要扣，缓存被清空或换设备时一次扣几十上百个；配额用光后，用户没点几个词就看到「今天的免费查词用完了」。配额本该数用户点了几次，ADR-029 的「80% 免费用户碰不到、10–20% 偶尔撞到」也是按点击估的。

只把预取改成不扣不行：QUERY 一次最多 100 个词，请求限流（ADR-060，按请求每秒 5 个、桶容量 60）只管请求数，不管词数，一个脚本每秒能读 500 个词；ECDICT 第一次查到的词还会写回 `words` 表，没有总量限制的读释义能把整本 ECDICT 抄进应用库。服务端也不能相信客户端自称「这是预取」。

我们决定：**QUERY 里该用户查过的词（生词本里查词次数大于 0 的词，已认识的也算）不扣每日查词配额，其余的词照旧每个扣 1；记查词的 POST 照旧每次扣 1。** 是不是查过的词由服务端判定，与请求来自预取还是点击查词无关。

## Decision

### 1. 扣多少

| 请求 | 每日查词配额 |
| ---- | ---- |
| QUERY（`/api/dictionary/entries` 或 POST 回退 `/api/dictionary/entries/query`）中查过的词 | 不扣 |
| QUERY 中没查过的词 | 每个扣 1 |
| `POST /api/me/word-lookups`（记查词） | 扣 1 |

结果：

- **预取**：只取有单词高亮的词，高亮来自复习词表（ADR-069），都是查过的词，所以正常的预取不扣配额。
- **点查过的词**（不管认不认识）：缓存命中只发 POST，没命中 QUERY 不扣、POST 扣 1，都算 1。
- **第一次点一个新词**：QUERY 扣 1，POST 扣 1，共 2（与 ADR-079 相同）。
- **Side Panel 锚点词等只读拉取**：查过的不扣，其余每个扣 1。

### 2. 「查过的词」怎么判定

- 查过的词：该用户 `user_dicts` 里查词次数大于 0、词条没被删除的词，**不管是否标记认识**。它比复习词表（ADR-069，不含已认识的词）大：复习词表决定单词高亮，已认识的词没有高亮；但认识的词也是点击查过、扣过配额的，再读它的释义同样不该扣。复习词表的定义不变。
- QUERY 先按 ADR-079 Decision 1 规范化、去重，再把每个词与该用户查过的词的 `English` 不区分大小写地比对（`words.english` 本来就是 `COLLATE NOCASE`，ADR-043）。比对上的不扣，其余的词数一次性扣。
- 一批里全是查过的词时不调用配额计量，也不写计数表；用户当天配额用完后，这样的 QUERY 仍然放行。
- 读查过的词出错时，这一批按「都没查过」扣（只记 warning）。免费必须由服务端确认，不因出错而放开总量；预取被拒本来就静默，点击查词只多扣 1。
- 规则放在 `dictionary.Entries.Lookup`，查过的词通过构造函数传入的接口读（AGENTS.md 的 DDD 分层），单元测试用假实现。

### 3. 防护靠什么

- **总量**：免费的只有用户自己查过的词。每个词第一次被查时，那次点击已经扣过配额；本地词典缓存 30 天有效，所以每个用户每 30 天的免费读取大约就是生词本的大小。查过的词在 `words` 表里已有一行，读它们不会触发 ECDICT 写回。没查过的词照旧受每日查词配额限制，脚本拖不走整本词典。
- **速度**：请求限流（ADR-060）不变。
- 不新增防护计数，不改计数表结构。

### 4. 免费档额度怎么估

ADR-079 Decision 8 的「上线前调高免费档」不变，但估算改了：每日查词配额 ≈ 点击查词次数 + 当天第一次点的新词数，预取不计入。具体数值仍由 Linear WIL-498 定。

## Considered Options

- **QUERY 一律不扣配额，只靠请求限流**：最简单，但限流按请求计，一次 100 个词只算 1 个请求；没有总量限制，ECDICT 写回会让应用库无限增长。否决。
- **请求限流改按词计（`AllowN(n)`），另给 QUERY 一个桶**：能限速度，但总量仍然没有上限，还多一组要调的数值。否决。
- **客户端声明「这是预取」，服务端据此不扣**：客户端可以伪造，等于 QUERY 一律不扣。否决。
- **QUERY 一律不扣用户配额，另设一个用户看不到的每日上限，只数没查过的词**：点一个新词也只扣 1，但多一个计数和一个要调的值，碰到它时还要区分两种 429。否决（用户 2026-11-11 选了更简单的规则，新词按 2 估额度）。
- **按请求来源免费（预取请求不扣、点击请求照扣）**：服务端分不清预取和点击，最终还是要信客户端。否决，改为按词判定；点击没命中缓存时，查过的词也因此不多扣。
- **只有复习词表里的词免费（不含已认识的词）**：与单词高亮同一个集合，但点一个已认识、缓存过期的词要扣 2，而它和没认识的词一样早就扣过配额。否决（用户 2026-11-11 定：查过的词都算）。

## Consequences

- 修订 ADR-079：Decision 1 表格「每日查词配额」一行改为「没查过的词每个 +1」；Decision 5「扣 n」里 QUERY 的 n 改为没查过的词数，「余量不够时预取先于点击被挡」不再成立（预取的词根本不扣）；Decision 8 的估算按本 ADR Decision 4。ADR-079 Considered Options 否决的「QUERY 只返回复习词表里的词」仍然否决：QUERY 照旧能读任何词，只是扣不扣配额按是不是查过的词区分。
- 预取不再消耗配额，点击查词不会因为预取被 429 挡住；配额重新接近「今天点了几次」。定价页免费档不写具体次数的决定（ADR-079 Consequences）不变。
- QUERY 每次多一次按用户读查过的词的查询（`user_dicts` 按 `user_id` 加 `words` 主键 join），代价很小。
- enx-chrome、enx-ui 不用改：客户端照常发 QUERY，扣不扣由服务端定。
- 隐私不变：判定只用已有的生词本数据，不新增存储。
- 实现另开 issue（enx-api）。
