# ADR-061：扩展在本地缓存词典释义；命中缓存时由记查词次数的 POST 顺带计量

现在每次点击查词都要发两个请求：先 `GET /api/translate?word=` 拿释义，再 `POST /api/me/word-lookups` 给查词次数加一（ADR-059 Decision 3）。同一个词点第二次，不管是在同一页面的另一个段落，还是两周后在另一个网站，GET 返回的词典释义都一样。扩展里唯一的缓存是 content script 的 `wordCache`，它只在内存里，只属于一个标签页，而且点击查词的流程也不读它。

我们决定：

- **扩展在 `chrome.storage.local` 里缓存词典释义**，只存词典本身的字段，不存用户状态。所有站点、所有标签页共用一份，浏览器重启后还在，30 天过期。
- **命中缓存时不发 GET，只发 POST，并带上 `fromCache: true`。** 服务端看到这个标记，就替这次查词扣每日查词配额、写查词事件，然后照常给查词次数加一，返回新的查词次数和「认识」状态。超额时返回 429，扩展不显示缓存里的释义，与没有缓存时一样按超额处理。

## Decision

### 1. 缓存什么：只存词典数据

缓存条目只存 GET 返回的词典字段：`Id`、`English`、`Pronunciation`、`Chinese`、`WordType`。

- **不存** `LoadCount`、`Known`：它们属于用户，会被别的设备、enx-ui、标记认识改掉。命中缓存时由 POST 的返回值提供（Decision 3）。
- **不存** `AIFallback`：查不到时才有，取决于服务端当时的设置和用户的积分。
- **查不到的词不缓存**（没有 `Id`）。词库随时可能补上这个词，查不到时还要给出 AI 兜底的入口。
- **AI 写的释义不缓存**（`Origin: 'ai'`，ADR-045）。它可能被管理员复核、修改，也不该在本地长期留下一份没复核的释义。
- 键是点击的词形，trim 并转成小写。GET 可能把词形归到原形（点 "ran"，返回 "run" 那一行），缓存按点击的词形存，"ran" 和 "run" 可以各存一条、指向同一个 `Id`。
- 词典数据对所有用户都一样，没有隐私问题，所以缓存**不按用户分开**。

### 2. 存在哪：`chrome.storage.local`，由后台 Service Worker 管

- 不用 `window.localStorage`：在 content script 里，它属于**当前网站**（比如 infoq.com），换个站点就读不到，网站自己的脚本还能读写、清空它。Service Worker 里则根本没有 `localStorage`。
- 不用 IndexedDB：几千条小对象，`chrome.storage.local` 足够，不值得多一套 API。
- 后台 Service Worker 是唯一读写缓存的地方。主窗口查词浮层和 Side Panel 本来就通过后台的 `getOneWord` 查词，缓存放在那里，两边都能用上。#212（同一页面重复点词不重查）也由这份缓存覆盖，不再单独让 content script 的 `wordCache` 走点击流程。
- 每个词一个键：`dictCache:v1:<词>` → `{ entry, cachedAt, lastUsedAt }`。读写一条只碰一个键，不用每次读写整个缓存对象。
- 键名带格式版本号 `v1`。缓存格式变了，或者词典有一次大的整体更新，就把版本号加一；旧前缀的键在下一次清理时删掉（Decision 5）。
- 缓存逻辑（命中、过期、淘汰、写不写入）放在 `src/lib/` 里，存储作为参数传进去，用假的存储做单元测试（AGENTS.md「I/O enters through the constructor or the parameter list」）。

### 3. 一次点击查词怎么走

只有**一次点击查词**（主窗口点词、Side Panel 里点句中的词）才走缓存。Side Panel 只读的拉取（镜像卡片、重试、句子的锚点词）照旧发 GET，因为它们要的是服务端当前的查词次数。

**命中缓存**（有这个键，且没过期）：

1. 发 `POST /api/me/word-lookups`，body 为 `{"wordId": "…", "fromCache": true}`。查词浮层像现在等 GET 一样显示加载中，**等 POST 返回之后才显示释义**。
2. 根据 POST 的结果：

| POST 返回 | 扩展怎么做 |
| ---- | ---- |
| 200 `{queryCount, known}` | 缓存的释义加上返回的查词次数和「认识」状态，用来显示浮层、画单词高亮、同步到 Side Panel；更新这一条的 `lastUsedAt` |
| 429 `lookup_quota_exceeded` | 不显示释义，按超额处理，与 GET 超额时完全一样 |
| 429 `too_many_requests`（ADR-060） | 与 GET 被限流时一样处理 |
| 401 | 与现在一样，提示会话过期 |
| 404（`Id` 已不存在） | 删掉这一条缓存，改走「没命中」的流程 |
| 网络错误、5xx | 照样显示缓存的释义，查词次数和高亮不变；这次查词可能没记上，与 POST 现在丢失时一样 |

**没命中**（没有这个键，或已过期）：与现在一样，先 GET（GET 负责计量），再发不带 `fromCache` 的 POST。GET 返回的词符合 Decision 1 就写进缓存，过期的条目也这样被刷新。

- POST 仍然**不重试**（ADR-059 Decision 3）：它不幂等，带上 `fromCache` 后还会写查词事件。
- 网络错误时显示缓存的释义，等于「出错放行」（ADR-029 E2），只是放行发生在客户端。

### 4. 服务端：POST 带 `fromCache: true` 时先计量

`POST /api/me/word-lookups` 收到 `fromCache: true` 时，按这个顺序做：

1. 词不存在 → 404，不计量。先查存在再计量，否则扩展收到 404 后改发 GET，同一次点击会被计两次配额。
2. 扣每日查词配额、写一行查词事件，用的就是 GET 里那个 `QuotaMeter.Charge`。超额 → 429，响应体与 GET 超额时相同（`dictionary.RespondQuotaExceeded`），查词次数不加。
3. 查词次数加一，返回 `{queryCount, known}`，与现在一样。

- 不带 `fromCache`（或为 `false`）时行为不变：不计量，只给查词次数加一。还没升级的扩展不受影响。
- 计量规则仍然只有一份 `QuotaMeter`，但调用它的地方从一处（`Resolve`）变成两处。这修订了 ADR-018「查词唯一入口」和 ADR-059 Decision 3「POST 不扣配额」：**一次点击查词只计量一次**，没命中时在 GET 上计，命中缓存时在 POST 上计。「带 `fromCache` 才计量」这条规则放进 domain 包（例如 `dictionary`），handler 只做 HTTP 翻译。
- 计量失败照旧放行（ADR-029 E2）：`Charge` 出错只记 warning，照常给查词次数加一。

### 5. 过期、容量与淘汰

**过期：30 天，从写入时算起，命中不续期。**

- ECDICT 是只读的第三方数据，几个月才换一次版本；`words` 表里的释义只在管理员纠错时改，很少发生。
- 释义晚 30 天更新没什么坏处，大不了用户多看到几周旧的释义；而一个读者的生词要几周才会换一批，30 天能覆盖大部分重复查词。
- 命中时不续期：否则常查的词永远不会过期，也就永远拿不到更正过的释义。

**容量：最多 5000 条，单条超过 1 KB 不缓存。**

- `chrome.storage.local` 默认上限 10 MB，而且扩展其他数据（`swlog`、统计上报、服务端设置等）也存在里面。缓存的上限按 10 MB 的一半来算，不能把它占满。
- 本地 ECDICT 里常用词（`frq` 前 2 万）的释义加音标平均不到 100 字节，最长不到 400 字节；算上 JSON 和时间戳，一条大约 300 字节，5000 条约 1.5 MB。单条上限 1 KB，最坏情况也只有 5 MB。
- 不申请 `unlimitedStorage` 权限：用不到，而且多一项权限会让安装页多一行提示。

**淘汰：先删过期的，再按最近使用时间删最旧的。**

- 写入一条新的之后，如果条目超过 5000 条，就先删过期的、再删 `lastUsedAt` 最早的，一直删到 4500 条。留出 500 条的余量，不必每写一条就清理一次。
- Service Worker 启动时也做一次同样的清理，顺便删掉旧版本前缀的键。
- 按最近使用时间删（LRU），不按使用频率删（LFU）：按频率删要在本地另外记次数，而一个去年查过 20 次、早就会了的词会一直占着位置。最近用过的词更可能再被点到；词的使用频率服务端已经有了（查词次数），本地不再记一份。
- 写入失败（比如存储满了）只记 `swlog`，不影响这次查词。

### 6. 登出时尽力清空

- 用户主动登出时，删掉所有 `dictCache:` 键。删除失败不处理，不重试：缓存里没有用户数据，留下来也没有影响。
- 换账号、会话过期不清空。

## Considered Options

- **把计量从 GET 整个移到 POST**：GET 只读释义、没有副作用，最干净。但配额就只拦 POST 了，任何人直接调 GET 就能绕过每日查词配额，只剩令牌桶兜底。否决。
- **命中缓存不计配额、不进统计**：服务端不用改。但「今天查了几个词」、活跃用户都会偏低，免费用户还能靠缓存无限次地查以前查过的词。否决。
- **超额时照样显示缓存里的释义**：缓存词不花服务器成本，体验更好。但每日查词配额是产品规则，有没有缓存都应该一样拦。否决（用户 2026-10-19 定）。
- **连用户状态（查词次数、「认识」）也缓存**：命中时可以一个请求都不发。但别的设备、enx-ui 都会改用户状态，缓存很快就和服务端对不上，单词高亮会画错。否决。
- **用 HTTP 缓存（GET 加 `Cache-Control`）**：GET 有副作用（计量），响应里还带每个用户的查词次数，不能交给浏览器缓存。否决。
- **只在内存里缓存（#212 原来的方案）**：只能覆盖同一个标签页、同一次页面加载。被本 ADR 包含。

## Consequences

- **省下的是请求数和服务端的词典查询，不是等待时间。** 命中缓存时一次点击只发一个请求，服务端不跑 `Resolve`、不读 ECDICT；但浮层要等 POST 返回才显示，所以等待时间和现在等 GET 差不多。
- **先上线 enx-api，再发扩展。** 新扩展遇到旧 enx-api 时，旧 POST 会忽略 `fromCache`，命中缓存的查词就不计配额、不进统计。
- ADR-059 Decision 3 的表格里「POST：查词事件 / 配额：不写，不扣配额」要改成「带 `fromCache: true` 时写」。实现时一并更新 `handlers/word_lookup.go` 的注释（「It is not a lookup request either: no quota, no lookup event.」）。
- 管理员在数据库里更正了某个词的释义，扩展最多 30 天后才会显示新释义。需要立即生效时，把 Decision 2 的版本号加一，所有缓存一起作废。
- 生产库被重置时（例如录 Demo 前清空 `enx.db`），旧缓存里的 `Id` 都会失效，POST 返回 404，扩展删掉这条缓存、改走 GET，自动恢复。
- 实现另开 issue，#212 并入那个 issue。
