# ADR-089：分屏时，同一分屏的两个标签页共用一份 ENX 侧边栏

Chrome 分屏（Split View，Chrome 140+）里两个标签页同时可见，但只有一个是活动视图，点哪边哪边就成为活动视图。Chrome 帮助文档明确写着：标签页专属的侧边栏「在视图之间切换时会收起」，Bookmarks 这类全局侧边栏才保持打开。所以这是 Chrome 的预期行为，不是 bug。

ADR-050 之后 ENX 只有标签页面板，于是典型用法「左边中文译本、右边英文原文 + ENX 侧边栏」里，焦点每在两边之间切一次，侧边栏就收起或展开一次，两个视图的宽度跟着变，正文整体重排（微信读书在单页和双页之间来回跳）。用户实测：在另一边的标签页上也打开一个 ENX 面板后，宽度就稳定了。

我们决定：**某个标签页的 ENX 侧边栏打开时，如果它在分屏里，就把同一份面板也登记到分屏里的另一个标签页上**，两边显示同一页文章的内容，焦点在两边切换时侧边栏不收起、宽度不变。

## Decision

1. **面板的归属不变，只是多一个「镜像登记」。** 打开面板的那个标签页（称为所属标签页）仍是内容的主人：面板 URL 仍是 `sidepanel.html?tabId=<所属标签页>`，存储 key 仍按所属标签页拆分（ADR-050 Decision 2、3 不变）。分屏里另一个标签页用**同一个 URL** 调 `setOptions({ tabId: <另一个>, path, enabled: true })`，它的面板显示的就是所属标签页的句子和查词。
2. **一个分屏只有一份 ENX 面板。** 在分屏任一边打开 ENX，都以这一边为所属标签页，覆盖两边的登记。两边各显示各的面板（例如左右都是英文文章）不在本 ADR 范围内。
3. **两个标签页都要 `setOptions` + `open()`，且都在同一个用户手势里。** 实验（#945，Chromium 158）：只对伙伴 `setOptions` 不 `open()`，焦点切过去面板照样收起；对非活动的伙伴调 `open({ tabId })` 会成功，面板在它第一次成为活动视图时才创建（那时才触发 `onOpened`）。手势之外调用 `open()` 会被拒绝。**分屏关系由 background 同步维护**：`open()` 必须在用户手势里同步调用（ADR-050 Decision 1），来不及 `await tabs.query`。background 维护「标签页 → 分屏伙伴」的缓存：Service Worker 启动时用 `tabs.query({})` 读 `Tab.splitViewId` 建表，之后靠 `tabs.onUpdated` 的 `changeInfo.splitViewId` 和 `tabs.onRemoved` 更新。打开时同步读缓存，两个标签页的 `setOptions` 与 `open` 在同一个同步块里发出。
   - **每个打开入口自己拿到伙伴。** `openTabSidePanel(tabId, partnerTabId?)` 只负责在同一同步块里发出两边的调用，伙伴由调用方传入。background 的两个入口（右键菜单、整句翻译消息）读上面的缓存。popup 是另一个上下文，读不到 Service Worker 的内存：popup 挂载时本来就 `await tabs.query` 找活动标签页，顺带读它的 `splitViewId`，再在同一窗口里找同一 `splitViewId` 的另一个标签页，记下伙伴；点击时同步传入。点击早于这次查找完成时，沿用现有的 `openActiveTabSidePanel()` 后备，查完再一起打开（尽力而为）。
   - **Service Worker 冷启动。** 右键菜单或整句翻译消息唤醒 Service Worker 时，`tabs.query({})` 的建表还没完成。此时事件自带的 `tab` / `sender.tab` 上的 `splitViewId` 能同步看出它在分屏里，但伙伴未知：先在手势里同步打开所属标签页（即 ADR-050 的行为），再等建表完成后对伙伴尽力补一次 `setOptions` + `open()`；Chrome 因手势已失效拒绝时只记日志。结果是冷启动后的第一次打开可能只有一边有面板，用户再打开一次即两边都开，与 Decision 4 第三条同类。popup 入口不受影响。
4. **两边同生同灭，尽力而为。**
   - **哪边是所属、哪边是镜像，只看 Chrome 里的登记。** 手势里同步发出的 `setOptions` 就是权威状态：每个标签页登记的 `path`（`sidePanel.getOptions({ tabId })` 可读回）里的 `tabId` 就是它的所属标签页；`path` 指向别的标签页的就是镜像。不另存配对记录，Service Worker 重启后也照此读回。
   - **用户在任一边关闭面板**（`sidePanel.onClosed`，Chrome 142+，与 manifest 的 `minimum_chrome_version` 一致）→ 注销并关闭另一边。另一边由登记推出：被关的一边是镜像时是它 `path` 指向的所属标签页，自己是所属时是分屏缓存里的伙伴。只有另一边的登记已启用、`path` 与被关面板的 `path` 相同才动它；先 `setOptions({ tabId, enabled: false })` 再关闭。
   - **不是用户关闭的 `onClosed` 忽略。** 被关面板的 `path` 不等于该标签页当前登记的 `path`（换主人时被新登记替换掉的旧文档），或该标签页的登记已停用（我们自己收尾注销的），都什么也不做，所以换主人不会关掉新面板，两边也不会互相递归关闭。
   - **分屏解除或标签页关闭** → 注销失效的镜像：标签页 X 离开分屏（`onUpdated` 的 `splitViewId`）或被关闭（`onRemoved`）时，检查 X 本身（未关闭时）和 X 原来的分屏伙伴（监听器更新缓存前取出）；登记已启用、`path` 指向的标签页已不存在或已不在同一分屏的，`setOptions({ tabId, enabled: false })`。Service Worker 刚重启、缓存里没有原伙伴时，改为检查 X 所在窗口的全部标签页（整窗关闭时跳过）。
   - 已打开面板的标签页之后才进入分屏：`onUpdated` 里没有用户手势，`open()` 会被拒绝，无法自动补开。用户在分屏里再点一次打开 ENX 侧边栏（任一路径）即可两边都开；不做自动补开。
   - **竞态不处理（owner 决定，见修订记录）。** 不用串行队列，也不在 `await` 前后重新核对。清理进行中又有手势改写登记、清理等待期间两个标签页又并入同一分屏、Service Worker 建缓存期间送达的分屏事件，这类交错都按最终读到的状态处理，结果可能是残留一个镜像面板、多关了一边或开关状态不对。代价只是界面：卡片列表在 ADR-090 的存储里，不丢数据，也不多调 AI；用户关掉或重新打开一次 ENX 即恢复。
5. **「内容属于谁」和「这个标签页上有没有打开的面板」分开判断。** `isTabSidePanelOpen(tabId)` 比对的是 URL 里的 `tabId`，回答的是「这个标签页自己的内容面板开着没有」，保持不变，整句翻译的已打开探测（`handleOpenSentencePanel`）仍用它。popup 的按钮要回答的是后者：活动标签页是镜像（登记的 `path` 指向别的标签页）时，按它的所属标签页的面板是否打开来判断；按钮因此显示「关闭」，点击关闭镜像这边，再由 Decision 4 关掉另一边，而不是把主人换成镜像这边。popup 的 `onOpened` / `onClosed` 同步也要认镜像标签页的 id。

## Considered Options

- **用 `windowId` 打开全局面板**：分屏切换时不收起，但会跟到窗口里所有标签页上并显示别页内容，正是 ADR-050 要消除的问题。否决。
- **只在 Chromium 报 issue，等上游改**：帮助文档已把收起写成预期行为，短期内不会变。仍要报一个 feature request（另行跟踪），但不作为解决办法。
- **让用户自己在另一边也打开一次面板**：用户已验证能稳定宽度，但另一边是空面板，焦点切过去就看不到翻译，每次分屏都要手动做一遍。否决，只作为临时绕法。

## Consequences

- 两边的面板是 Chrome 的**两个实例**（`setOptions` 文档：同一 path 登记到不同标签页即不同实例），两个都会存活。ADR-023 的卡片列表原本只在面板内存里，两个实例会内容不一致、每句各调一次 AI；所以卡片列表先按 ADR-090 存进 `storage.session`、事件由一个面板认领，两边才真正一致，一次操作只调一次 AI。滚动位置、展开状态各面板各自一份。
- 焦点在镜像那边时（例如在中文页上悬停），产生的查词写入的是镜像标签页自己的 key，不会出现在共用面板里。这符合「面板属于英文原文那一页」。在镜像那边点「整句翻译」则不同：它和其他入口一样会打开 ENX，按 Decision 2 镜像这边成为新的所属标签页，两边改显示它的卡片列表（ADR-090 按所属标签页存），原所属标签页的卡片仍留在自己的 key 下，在那边重新打开 ENX 即可回来。
- Service Worker 冷启动后的第一次右键菜单或整句翻译打开，可能只开所属那一边（Decision 3）。
- 分屏面板的打开、关闭和清理是尽力而为的（Decision 4 最后一条）：少见的交错下可能残留或多关一个面板，用户重新打开或关闭一次 ENX 即恢复。
- ADR-050 Consequences 第 3 条（切到别的标签页就没有面板）对分屏伙伴不再成立；对分屏之外的标签页仍然成立。

## 修订记录

- 2026-11-16，issue #945（规格评审第 1 轮）：Decision 3 补充每个打开入口如何拿到伙伴（popup 挂载时自己查 `splitViewId`，background 读缓存），以及 Service Worker 冷启动时先只开所属一边、再尽力补开伙伴；Decision 4 新增存在 `storage.session` 的配对记录、先删记录再关另一边、按 `onClosed` 的 `path` 忽略换主人造成的关闭；Decision 5 把「内容属于谁」和「标签页上是否有打开的面板」分开，popup 在镜像标签页上显示「关闭」；Consequences 写明镜像那边的整句翻译会换主人。原因：popup 读不到 Service Worker 的内存；分屏关系分不出主从，重启后也找不回镜像；原 Decision 5 会让镜像上的 popup 按钮把关闭变成换主人；原 Consequences 与 Decision 2 矛盾。
- 2026-11-16，issue #945（规格评审第 2 轮）：Decision 4 改为以 Chrome 的登记（`sidePanel.getOptions` 读回的 `path`）为所属关系的权威，配对记录只作重启后的索引；记录写入改由 background 的串行队列完成（popup 打开后发消息交给 background），清理处理也进同一队列，每步先对照 `getOptions`；换主人造成的 `onClosed` 按「被关的 `path` ≠ 当前登记的 `path`」忽略。原因：`storage.session` 是异步的，旧面板的 `onClosed` 可能早于新记录写入，按记录判断会把替换后的面板关掉；popup 与 background 交错打开时，各自写记录可能留下比最新登记更旧的记录。
- 2026-11-16，issue #945（规格评审第 3 轮）：Decision 4 新增破坏性操作前立即重新读两边的 `getOptions`、读后不再 `await`；另一边由登记（镜像的 `path` 或分屏缓存）推出，只有另一边已启用且 `path` 与被关面板相同才关；与登记不一致的记录视为过期，删除且不用来挑目标；收尾时先注销另一边再关闭，第二次 `onClosed` 按「登记已停用」忽略；写记录要求两边都已启用。原因：登记在队列之外由手势同步改写，记录可能还指向旧主人，`await` 之间登记也可能变化，按过期记录挑目标会关错面板。
- 2026-11-16，issue #945（规格评审第 4 轮）：Decision 4 的解除分屏与标签页关闭清理不再按「镜像的 `path` 仍指向记录里的所属标签页」判断，改为「镜像登记的有效条件」：候选来自 X 本身、监听器更新缓存前取出的原伙伴、涉及 X 的记录，缓存缺失时再加 X 所在窗口的全部标签页；指向已不存在或不在同一分屏的标签页的已启用镜像登记一律注销。原因：记录仍指向旧主人时（popup 已按新主人登记、配对消息未处理），按记录核对会跳过清理，留下一个镜像面板；所属标签页关闭时同理。
- 2026-11-16，issue #945（规格评审第 5 轮）：清理步骤判断分屏关系改为在 `getOptions` 读回之后同步读分屏缓存（缓存由监听器在入队前同步更新），不再先用 `tabs.query` 取快照再 `await` 登记。原因：`getOptions` 等待期间用户可能把两个标签页重新并入同一分屏，按旧快照会注销一个已重新有效的镜像。
- 2026-11-17，issue #945（规格评审第 6 轮后，owner 决定简化）：Decision 4 去掉配对记录和串行队列，所属关系只从登记的 `path` 读；关闭、解除分屏、关闭标签页的清理改为尽力而为，不处理清理过程中的竞态（手势同时改写登记、等待期间重新并入分屏、建缓存期间的事件），写进 Decision 4 最后一条和 Consequences；Decision 5 改按登记的 `path` 认镜像。第 2–5 轮为这些竞态加的规则（记录写入核对、破坏性操作前重读、镜像有效条件的候选集、缓存同步判断）随之删除。原因：评审连续 5 轮在越来越窄的交错上找新问题，规则越堆越多仍未收敛；这些交错几乎碰不到，后果只是界面上残留或多关一个面板，重新打开即恢复，不丢数据也不多扣费。
