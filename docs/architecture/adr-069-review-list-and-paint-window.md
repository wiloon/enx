# ADR-069：下划线改用一次取回的复习词表，只绘制当前屏附近——性能不再随文章长度变差

单词高亮原本按「一篇文章」设计：启用学习模式时把全文去重后的词分块发给 `paragraph-init`，全部取回后给全文注册下划线，之后每次查词都重建全文高亮。放到一整本书上这三步都出问题。所有者决定：**启用学习模式时一次取回用户的复习词表，取词请求不再随文章变长；只绘制当前屏上下约 1 屏内的下划线，词状态变化时只更新这个词。** 长文、短文走同一条路径。

这个决定并不难撤销，严格说够不上 ADR 的门槛。仍然写下来，是因为它修订了 accepted 的 ADR-011，而且「为什么要有窗口」的实测数据放在 issue 里，issue 关闭后很难再被找到。

## 背景：实测数据

样本是一本 Project Gutenberg 的书（`pg79871-images.html`）：约 7.4 万词，去重后约 9 千词。数据在 2026-10-30 用本机 Mac 的 Chrome 测得，下划线由脚本注册（均匀分布），没有启用真实扩展。

**滚动。** 注册的 `Range` 越多越卡，屏幕外的也算：

| 全书 `Range` 数 | 每帧耗时中位数 | 最慢一帧 |
|---|---|---|
| 0 | 16.7ms | 19.6ms |
| 200 | 16.7ms | 23.7ms |
| 1,000 | 22.4ms | 97ms |
| 3,000 | 32.6ms | 160ms |
| 6,000 | 42.4ms | 223ms |
| 12,000 | 60.8ms | 308ms |

**全量重建。** 遍历、切词、建 `Range`、注册并等下一帧，单次约 150～210ms，其中遍历和切词约 100ms。

**请求。** 这本书现在要约 47 个 `paragraph-init` 请求（每块 200 个不重复的词），接近 ADR-060 的桶容量 60，同时开两本书就可能撞 429。模拟从头读到尾：滚动中按窗口取词要 152 次；攒满 200 个新词向前预取要 45 次。

**词表大小。** 用书里的词（平均 7 个字母）生成样本，实际压缩得出，三档由样本结果折算：

| 复习词表 | 未压缩 | gzip |
|---|---|---|
| 3,000 词 | 约 48KB | 约 14KB |
| 5,000 词 | 约 80KB | 约 22KB |
| 10,000 词 | 约 165KB | 约 43KB |

## 决策

### 1. 复习词表

- **新接口 `GET /api/me/review-words`**，返回当前用户 `query_count > 0 AND known = 0` 的词和查词次数，格式是紧凑数组 `[["word",3], …]`。不带释义，不带已认识的词。走现有的认证和限流。
- **不复用 `GET /api/me/words`**：它是给 `/words` 页用的分页接口，要把整个词表取完得翻很多页，还带着页面用不上的字段。
- **下划线的判断不变**：词表里没有的词不画线，和 `isReviewable` 的规则一致。
- **同一页面只取一次**，存在内容脚本内存里，X 切换推文不重取。`paragraph-init` 留给旧版扩展，等旧版消失再删。

### 2. 绘制窗口

- 正文按块级元素分段，用 `IntersectionObserver` 维护**绘制窗口：当前屏上下约 1 屏**。窗口大小是常量，上线后可调，不写死在本 ADR。
- 段落进入窗口才切词和建 `Range`，离开窗口就移除下划线和相关记录。
- 窗口内的 `Range` 数量因此与文章长度无关。这是本 ADR 要守住的性质，不是一个优化。

### 3. 词状态变化时只更新这个词

- 维护两个索引，只覆盖窗口内的段落：**段落 → 词的位置**（段落离开时移除），**词 → 位置**（状态变化时更新）。
- **索引记录窗口内每个词的位置（文本节点 + 起止偏移），不只记有下划线的词。** 第一次查的词还没有 `Range`，但它在窗口内的所有位置都要出现下划线。需要画线时才建 `Range`。
- 词状态变化时比较新旧复习档位：没变就什么都不做；变了只移动这个词的 `Range`。
- 查词、标记认识、AI 兜底和侧边栏查词（adr-053）都只更新内存词表，再走这一条路径。已认识的词再被查一次回到复习（P-7、adr-059），同样由这条路径把下划线加回来。
- 窗口外同一个词不用管，段落进入窗口时按最新状态绘制。

### 4. 领域核心

绘制窗口和索引放进 `enx-chrome/src/lib/` 的一个模块，只暴露进入段落、离开段落、词状态变化和清空。`Highlight` 注册和文本节点读取从参数传入，单元测试跑在假对象上。`content.tsx` 只接 `IntersectionObserver` 和消息。

## 考虑过的方案

- **维持全文绘制，只懒加载词状态**：滚动卡顿来自注册的 `Range` 数量，取词懒加载解决不了。
- **滚动中按窗口取词**：要保留前端窗口、预取、防抖和失败处理，整本书仍要 45 次请求，还要把页面文字发给后端。词表方案每页 1 次，也不再发送页面文字。
- **查词后整体重绘窗口，不要索引**：约 1,500 词按比例估算约 2ms，性能上够用，也更简单。所有者选择精确更新：多数点击不跨档，本来就不该有任何重绘。
- **把词表持久化到 `chrome.storage.local`**：每篇省一次约 22KB 的请求，却要处理多设备过期、切换账号和退出登录时的清除。先不做。需要时可以用 `COUNT` + `MAX(updated_at)` 生成 ETag、走 304，这是纯增量改动。条件：词表普遍超过约 2 万词，或指标显示这个接口的耗时或流量成了问题。
- **在 enx-api 里加 gzip**：生产环境的 Cloudflare 已经压缩 JSON（`/api/version` 实测 `content-encoding: br`）。发布时确认新接口也压缩了；如果没有，再给这个路由单独挂中间件。

## 后果

- **快速滚动时下划线可能晚一点出现。** 所有者接受。
- **其他设备的更新要刷新页面才看到。** 同一设备的其他标签页和现在一样不同步。
- **启用结果的含义要改。** 新用户的复习词表可以是空的，这是成功；现有的「没取到词就算失败」不再成立，取词请求本身失败才算失败。
- **ADR-028 的总词数仍要切一次全文**，只在启用时跑一次（实测全书约 20ms），也只在本地。
- **已知限制：** 正文只有一个超大块级元素（比如整本书放在一个 `<div>` 里，靠 `<br>` 分行）时，这个段落的 `Range` 数量没有上限，窗口退化成全量绘制。实现时测，真遇到再按文本节点细分。
- **静态页面仍不监听 DOM 变化**（adr-011 F1）。宿主页面改了文本节点内容，已记录的偏移会失效，和现在宿主大改 DOM 时会错位是同一类限制。
- **ADR-060 的请求估算会变小**：`paragraph-init` 分块那几行随实现过时，起始值不用改。
