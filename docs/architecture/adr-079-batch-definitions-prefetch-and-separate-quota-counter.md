# ADR-079：批量读释义与预取；查词只由 POST 记，每日查词配额单独计数

ADR-061 之后，点过的词再点会立刻显示释义。但本地词典缓存只在点击查词时写入，所以**有单词高亮、本地却没有可用释义**的词，第一次点仍要等服务器：缓存过期（30 天）、存满被挤掉、在别的设备上查的、退出登录清空过、点的词形和上次不同。用户长期使用后，有高亮的词大多是很久以前查的，这种延迟会越来越常见；而一个词有高亮，正说明用户叫不准它，再点它的概率很高。

我们决定：

- **新增 `QUERY /api/dictionary/entries`**：一次读 1 个或多个词的词典释义，只扣每日查词配额，不写查词事件、不动查词次数，可以重试。所有「要释义但不是一次点击」的地方都用它，点击查词时本地缓存没命中也用它。
- **扩展打开页面时预取**：把正文里有单词高亮、本地缓存里没有可用释义的词凑成一批，用上面的接口取回，写进本地词典缓存。用户随后点它，走缓存命中的流程。
- **`POST /api/me/word-lookups` 是记一次查词的唯一入口**：每次点击查词都发，不管有没有命中缓存；它扣每日查词配额、写查词事件、查词次数加一。`fromCache` 不再有意义。
- **每日查词配额改用一张单独的计数表**（每个用户每个 UTC 日一行），不再数查词事件。查词事件只表示「用户查了一次词」。
- **每日查词配额对大多数用户设得很宽**：约 80% 的活跃免费用户正常阅读碰不到；10–20% 高频使用的免费用户偶尔撞到，由此产生付费意愿（ADR-029 的引导付费作用保留）。它同时是保护 API 的总量兜底。因为预取也占配额，免费档上线前调高。

## Decision

### 1. 读释义与记查词分成两个接口

| | `QUERY /api/dictionary/entries` | `POST /api/me/word-lookups` |
| ---- | ---- | ---- |
| 做什么 | 读 1–100 个词的词典释义 | 记一次查词（body `{"wordId"}`，与现在一样） |
| 每日查词配额 | 每个请求的词 +1 | +1 |
| 查词事件 | 不写 | 写一行 |
| 查词次数 | 不动 | 加一 |
| 返回 | 每个词的词典字段，查不到的词标明查不到 | `{queryCount, known}` |
| 重试 | 可以（安全；重试只让配额多算） | 不重试（不幂等，宁可少记一次，ADR-059 Decision 3） |

- 拆成两个接口的理由不变（ADR-059 Decision 3）：读释义是最常用的操作，必须能在网络抖动时重试；记查词不幂等，不能重试。把两者合成一个请求，最常见的「第一次查一个新词」就不能重试了；要能重试又不重复计数，得加查词 ID 去重，ADR-059 已因成本否决。
- 查词事件与查词次数从此都由 POST 写：先检查词存在，再扣配额、加次数、写事件。404 不扣配额；次数写入失败时已扣的配额保留且不写事件；事件写入失败只记日志，不撤销次数。缓存命中与否只决定客户端发不发 QUERY，不再决定服务端在哪边计量。
- QUERY 的请求体是 `{"words": ["…", …]}`，最多 100 个词，超过返回 400。上限按原始条目计；含空格（GET 的句子判定）或规范化后为空的条目使整个请求返回 400，且不扣配额。复用 GET 的 `SetEnglish` 规范化（保留大小写、统一撇号、去掉所有格），规范化后按区分大小写的形式去重，再一次性按不同词数扣配额。
- QUERY 返回数组，每项以请求的规范化词形为键，另带状态 `found`、`not_found` 或 `failed`；`English` 可以是不同的原形。命中返回词典字段（ADR-061 Decision 1 的 `Id`、`English`、`Pronunciation`、`Chinese`、`WordType`，以及 `Origin`，和释义来源 `Source`：`local` 或 `ecdict`，供 enx-ui `/lookup` 给管理员显示来源）；写回失败时省略空 `Id`。真正查不到时返回现有用户策略的 `AIFallback`（每次请求至多计算一次）；超时、数据源错误、ECDICT 不可用或存储错误标记 `failed`，不冒充查不到，也不给 AI 入口，其他词仍可返回。**不返回查词次数和「认识」状态**。点击查词时它们由随后的 POST 返回，与 ADR-061 缓存命中时一样；浮层先显示释义，POST 返回后补上次数和「认识」状态。
- 每个词仍由 `dictionary` 包解析：先 `words` 表，再 ECDICT，ECDICT 命中写回 `words`；AI 写的释义只对能用 AI 的用户返回（ADR-045）。QUERY 不触发 AI 兜底。
- 用 HTTP QUERY 方法（RFC 10008）：它和 GET 一样安全、可重试，又能带请求体，适合「按一批词读」。2026-09-29 实测 Chrome、gin、Cloudflare + nginx、Kong 都放行，`paragraph-init` 已使用带请求体的 QUERY；同时始终注册 `POST /api/dictionary/entries/query`，与 QUERY 共用 handler；enx-chrome 和 enx-ui `/lookup` 先发 QUERY，遇到方法被拒、请求体丢失或网络错误等传输失败时用同一请求重试 POST（ADR-041 C）。上线前仍在 homelab 验证 QUERY 请求体完整到达。
- enx-chrome 跨域请求会先发 OPTIONS 预检；现有 CORS 已允许 QUERY。enx-ui 不跨域：它请求同源的 `/api/*`，由 `src/proxy.ts` 转发给 enx-api，QUERY 及其请求体要经过这层转发；转发丢掉方法或请求体时由上面的 POST 回退兜住。请求必须是 JSON，否则返回 415；成功响应带 `Accept-Query: application/json`，与 `paragraph-init` 一致。

### 2. 每次点击查词怎么走

- **命中本地词典缓存**：立刻显示缓存里的释义；发 POST。
- **没命中**：发 QUERY（一个词），显示释义，按 ADR-061 Decision 1 写进缓存；词有 `Id` 就发 POST。查不到的词照现在的流程给出 AI 兜底入口；AI 兜底拿到释义后发的 POST 也照旧（ADR-059）。
- POST 的处理表与 ADR-061 Decision 3 相同（200 补上次数和高亮；429 释义留在屏幕上、在下方提示；404 删掉这条缓存，重新 QUERY 拿新的 `Id` 再发 POST；网络错误不重试）。
- 用户看到释义要等的仍只是一个往返（没命中时是 QUERY，与现在的 GET 一样）；POST 在释义显示之后异步发，与现在一样。

「这次算不算一次查词、要不要发 POST」的规则仍放在客户端的 `src/lib/`（enx-chrome 和 enx-ui 各一份，ADR-059 Decision 3），带单元测试。

### 3. 不是点击的读释义也走 QUERY

- Side Panel 翻译整句后为句子的锚点词建卡片、加载失败后点 Retry：先查本地缓存，没命中就 QUERY，不发 POST（ADR-061 Decision 3 的「只读拉取」）。现在它们没命中时发 GET，会写一行查词事件、被算进阅读统计和活跃用户；改走 QUERY 后不再算。
- enx-ui `/lookup` 的每次提交：QUERY 一个词，拿到 `Id` 后发一次 POST（ADR-059 #274 的规则不变，只是 GET 换成 QUERY）。QUERY 返回就显示释义；查词次数等 POST 200 后按其 `queryCount` 显示。POST 的处理与 Decision 2 的表一致：429 释义留在屏幕上、在下方显示 API 的提示（配额与限流各自的文案），不重试；其他失败不重试、不提示，只是不显示次数。较早一次提交的 POST 晚到时不得改写较新的结果。

### 4. 预取

- **时机**：每次正文处理运行在复习列表和高亮偏好加载后选词（复习列表与正文的交集，ADR-069），不等增量绘制窗口；SPA 重建和重新启用时也运行。
- **取哪些词**：有单词高亮、本地词典缓存里没有或已过期的词，按页面词形的 `wordKey`（缓存的键，ADR-061 Decision 1）去重；同一页面已在请求中或已取过的词不再取。超过 100 个就分批。
- **不按「读到哪一页」分段预取**：网页是连续滚动的，没有可靠的「页」；一篇文章里有高亮的词通常几十个，一条释义约 300 字节，一次全取回只有几十 KB。
- 预取由后台 Service Worker 发 QUERY，结果按 ADR-061 Decision 1 写进本地词典缓存（查不到的、AI 写的不写）。它**不发 POST**，不显示任何东西。
- **预取失败一律静默**：429（配额或限流）、401、网络错误、5xx 都不提示；除 Decision 1 的 QUERY 到 POST 传输回退和既有 401 刷新令牌外不重试，等用户点击时按 Decision 2 再取。预取只是让点击更快，任何情况下都不能打扰阅读，也不能改变点击查词的结果。
- 学习模式关闭、用户没登录、单词高亮关闭（ADR-053 的偏好）时不预取：没有高亮就没有要预取的词。

### 5. 每日查词配额：单独的计数表

- 新表 `dictionary_quota_usage`：主键 `(user_id, utc_day)`，列 `used`（已扣的量）、`rejected`（被拒的量）。每个用户每个 UTC 日最多一行。
- **扣 n**（QUERY 扣请求里的词数，POST 扣 1）：在一条语句里做「`used + n` 不超过上限就加上」，加上了就放行；加不上就把 `rejected` 加 n、返回 429（`lookup_quota_exceeded`，响应体不变）。整批要么全扣，要么全拒，不做部分放行。
  - 好处：余量不够一批预取时，预取被拒，单个词的点击查词仍能通过；预取天然先于点击被挡住。
- `rejected` 保留 ADR-029 C2 想要的信号（「有多少人撞墙、撞得多狠」），但不再让它进 `used`，也不再为被拒的请求写查词事件。
- 上限仍按订阅档位分两档，仍由 `stripe.quota.dictionary-lookup-daily-free` / `-subscribed` 配置，启动时必须大于 0（ADR-059）。
- 计数失败照旧放行（ADR-029）：读写计数表出错只记 warning，放行这次请求。
- 用现有 `stats.lookup-events.retention-days`（31–100 天）保留每日用量行，每小时清理超过该窗口的行；不建汇总表。
- 这张表带 `user_id`，注销账号时要一并删除（加进 `repo/account.go` 的 `personalTables`，ADR-062）。
- 计量规则放在 `dictionary` 包里（`QuotaMeter` 改为扣 n、读写这张表），handler 只做 HTTP 翻译。查词事件的写入从 `QuotaMeter` 移到记查词的 `dictionary.WordLookups.Record`。

### 6. 查词事件只表示一次查词

- 只有 `POST /api/me/word-lookups` 在放行之后写查词事件。**超额的 POST 返回 429，不写查词事件，也不加查词次数。**
- 查词事件不加类型字段：配额已经不靠它计数，它只剩一种含义。
- 新写的事件 `outcome` 都是 `allowed`；表结构不改，旧的 `rejected` 行随保留期自然删掉。阅读统计本来就只数 `allowed`，不受影响。
- 活跃用户（ADR-058）仍从查词事件推导。**只被拒、没有一次成功查词的用户，从此不算活跃用户**；被拒的量看 `dictionary_quota_usage.rejected`。

### 7. 旧接口与发布顺序

- `GET /api/translate?word=` 与 `GET /api/word/:word` 保留到旧版扩展和 enx-ui 都不再调用为止，行为改为「读一个词」：扣配额 1、不写查词事件。仍返回查词次数和「认识」状态，旧版扩展的浮层要用。
- `POST /api/me/word-lookups` 的 `fromCache` 字段被忽略，旧版扩展不受影响。
- 因此**先上线 enx-api，再发扩展和 enx-ui**。旧版扩展在新 enx-api 上的结果：没命中时 GET 扣 1、POST 扣 1 并写事件；命中时 POST 扣 1 并写事件。统计与新版一致，只是只读拉取不再被算成查词。
- 上线当天计数表从 0 开始，用户当天剩余时间相当于拿到一份新的额度。可以接受。

### 8. 免费档上线前调高

一次没命中缓存的点击查词扣 2（QUERY 1、POST 1），预取每个词扣 1。现在免费档默认 200，一个用了较久的用户读几篇文章就会用完，之后点新词也会收到 429，违背「配额不影响正常使用」。上线这套之前把免费档调高到正常阅读碰不到的值；具体数值随配置变更另定，不在本 ADR（Linear WIL-498）。

## Considered Options

- **一个请求同时返回释义、加查词次数、写查词事件**（没命中时）：少一个请求，查词事件和查词次数也在一起。但这个请求不能重试，而它恰恰覆盖最常见的「第一次查新词」。POST 本来就在释义显示之后异步发，合并也不会让用户更早看到释义。否决。
- **给查词事件加类型字段（点击 / 读取），配额数全部行、统计只数点击**：改动小。但配额和查词事件本来就是两回事，混在一张表里，每个读统计的地方都得记得过滤类型。否决，改为单独的计数表（用户 2026-11-10 定）。
- **配额继续数查词事件，QUERY 不扣配额**：QUERY 就成了不受总量限制的读释义接口，可以用它把整本词典拖走，只剩令牌桶限速。否决。
- **QUERY 只返回用户复习列表里的词**：能防止用它拖词典。但配额已经限住了总量，与 GET 现在的防护相同；多一道限制还要多查一次表，enx-ui `/lookup` 和点新词也用不了这个接口。否决，QUERY 能读任何词的释义（用户 2026-11-10 定）。
- **按请求扣配额，不按词**：一批 100 个词只算 1，配额形同虚设。否决。
- **余量不够时部分放行（能取几个算几个）**：预取能多拿几条，但点击查词可能被预取挤掉最后的余量。整批全拒能让点击优先。否决。
- **预取整个复习列表，不只本页**：一次填满缓存，换页也不用再取。但复习列表可能有几千个词，大多不在当前文章里，白白占配额和缓存位置。否决。
- **按阅读进度分段预取**（读第 1 页取第 1、2 页，读第 2 页取第 3 页）：网页没有可靠的「页」，要跟踪滚动位置；而一篇文章的高亮词一次就取完了。现有页面处理运行（包括 SPA 重建和重新启用）时重新选词。否决。
- **超额的 POST 也写一行 `rejected` 查词事件**（ADR-029 C2 原样保留）：查词事件就又不只表示一次查词了；被拒的量改记在计数表的 `rejected` 里。否决（用户 2026-11-10 定）。
- **继续用 GET 批量读（`GET /api/dictionary/entries?words=a,b,c`）**：不需要 QUERY，也不用改 CORS。但 100 个词放进 URL 会很长，还会出现在访问日志和 Cloudflare 日志里，泄露用户在读什么。否决；始终提供 POST 回退，以覆盖拦截 QUERY 的用户网络。

## Consequences

- 有单词高亮的词，第一次点时释义通常已经在本地，与缓存命中一样立刻出现。
- 修订 ADR-018：`Resolve` 仍是解析一个词的唯一入口，但不再自己计量；计量由调用方（QUERY、旧 GET、POST）按本 ADR 扣。
- 修订 ADR-029：计数从「查询请求数」改为「词典用量」（QUERY 的词数加 POST 的次数）；被拒的量单独记，不进 `used`。分档和引导付费的作用不变，目标仍是 10–20% 的活跃免费用户偶尔撞到上限（Linear WIL-176），数据改看 `dictionary_quota_usage`，保留期与查词事件相同。
- 修订 ADR-059：配额不再从查词事件推导；GET 不再写查词事件；POST 扣配额（Decision 3 曾否决「POST 也扣配额」，理由是它把配额当限流用，现在配额就是这个用途）；被拒的请求不写查词事件；活跃用户不含只被拒的用户。
- 修订 ADR-061：`fromCache` 作废；预取也会写本地词典缓存；只读拉取没命中时改走 QUERY。
- 配额数字不再等于「今天查了几个词」，对用户也不再这样解释；要看查了几个词，看阅读统计。
- **隐私政策要跟着改**：enx-ui 隐私页现在写查词事件用于「Your daily lookup limit」。改为配额来自一张只有每天用量的计数表，查词事件只用于阅读统计和活跃用户；列出每日查词用量计数（最多 100 天）；这些行只有每日每用户计数，没有词或页面。文案由 Linear WIL-498 跟踪并在上线前发布，不属于 #812；「查词事件不记是哪个词」的承诺不变。
- **定价文案要跟着改**：enx-ui `src/lib/plans.ts` 免费档写 "… 200 lookups a day"（`FREE_DAILY_LOOKUPS`）。配额包含预取之后，「每天 N 次查词」不再准确：用户没点几个词，用量也会上升。改法（用户 2026-11-10 定）：免费档不写具体次数（已被 ADR-080 Consequences 的 2026-11-13 修订取代：预取不扣配额后，定价页重新写出数字）；付费档「更高的每日查词上限」仍是卖点，ADR-029 Decision 8 的额度提醒和 429 的升级入口保留，只是文案不说「查了 N 个词」。与调高免费档一起做，见 Linear WIL-498。
- 实现另开 issue：enx-api（计数表、`QuotaMeter` 扣 n、QUERY 接口、POST 扣配额并写事件、旧 GET 改行为）、enx-chrome（点击查词改 QUERY、预取、只读拉取改 QUERY）、enx-ui（`/lookup` 改 QUERY）、配置（调高免费档）。

## 修订记录

- 2026-11-10，issue #812：补全批量接口的规范化、逐词结果与 AI 入口及 POST 失败顺序，纠正 QUERY 路由和 CORS 的现状，避免与现有点击流程及词典解析不一致。
- 2026-11-10，issue #812：按用户决定始终注册 POST 回退，并将每日配额用量保留期改为查词事件的保留窗口，以覆盖拦截 QUERY 的网络并支持历史撞额测量。
- 2026-11-10，issue #813：预取与缓存统一按 `wordKey` 识别页面词形，并明确现有重建与重新启用的处理时机，避免预取无法命中。
- 2026-11-11，issue #814：QUERY 的 `found` 项加 `Source`，纠正 enx-ui 经同源转发而非跨域请求的现状，并写明 `/lookup` 在 POST 返回前后与失败时的显示，以保住管理员来源标签并与点击查词的 POST 处理一致。
