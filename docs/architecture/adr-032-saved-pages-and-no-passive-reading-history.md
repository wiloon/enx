## Context

### 这个 ADR 是怎么来的

做 ADR-010 Decision 8（用户确认后上报无法处理的页面）时，产生了三个连带问题：

1. 移动端要能「在桌面收藏、在手机上接着读」——服务端得记住用户想读的文章。
2. 是否可以更进一步：默认记录用户的阅读历史，条款里声明、设置里可关？这样将来能做「大家都在读」的热度榜。
3. 收藏时存 URL，还是连同正文（乃至译文）一起存？

### 现状（以 2026-09-20 的代码为准）

- 服务端**不存**任何页面 URL，唯一例外是 `page_reports`（用户点击确认后才写，脱敏、90 天、每人 50 条）。
- 扩展**也不**在本地保存任何「按 URL 的阅读历史」：阅读进度水位只在内存里（`readingProgress.ts`），`chrome.storage.local` 里只有偏好、统计上报队列和诊断日志。所以「浏览历史只存本地」是**将来的设计**，不是现状。
- 服务端从未拿到过文章正文：`getWords` 只发去重后的单词列表，其余只有用户**主动选中**的句子（隐私页已如实写明）。
- Chrome 应用商店用户数据政策（[User Data FAQ](https://developer.chrome.com/docs/webstore/program-policies/user-data-faq)，2026-09-20 查阅）：涉及用户数据的披露「不能只放在隐私政策、服务条款或类似文档里」，必须在扩展界面内显著展示，并让用户在收集前「做一个明确表示同意的具体动作」；浏览活动只允许用于面向用户、且在商店页与界面里明确描述的功能。

### 用户规模

ADR-028 估计用户是「个位数到几百」。这直接决定「热度榜」在近期没有统计意义（Options E）。

## Options Considered

### A. 阅读历史怎么处理

| 方案 | 结论 |
| --- | --- |
| A1. 默认上传，注册条款里声明，设置里可关 | **否决。** ①Chrome 应用商店明文要求界面内先同意、且不接受仅靠条款披露，默认开启加事后关闭与此不相容，后果是下架；②个人信息保护类法规的方向是非必要处理须单独、自愿同意，不能捆绑在「同意条款才能使用」里；③与产品自己对外的承诺（「我们不记录你读的是什么」）正面冲突，且一旦改口，「我们曾经记录过」这个事实删不掉（ADR-028 的同一条理由） |
| A2. 默认关闭的 opt-in 上传（首次弹窗明确选择，与条款同意分开） | 合规上可行，但参与率低，且当前没有消费它的功能。**推迟**，见 Revisit Trigger |
| **A3.（采用）默认不记录；服务端零历史。本地历史可以有，但只存本机、永不上传** | 延续 ADR-028 的立场，条款如实写明，无需任何同意流程 |

### B. 保存文章时存什么

| 方案 | 结论 |
| --- | --- |
| **B1.（采用）URL + 页面标题** | 最低敏感。URL 本身不受著作权保护，标题是一句话的题名，是「稍后读」类产品的最小可用元数据。移动端靠这个 URL 重新打开页面 |
| B2. B1 + 服务端保存正文快照 | **否决。** 见 Rationale「为什么不存正文」 |
| B3. B2 + AI 译文（中文）一并存 | **否决，且比 B2 更严重。** 整篇译文是对原文的翻译（演绎）作品，翻译权、改编权是著作权人的专有权利；存的不再只是「一份拷贝」而是「我们生成的衍生作品」 |
| B4. 移动端在**设备本地**缓存自己打开过的页面，用于离线阅读 | **允许，不属于本 ADR 的服务端范围。** 副本在用户自己的设备上，服务端仍未持有正文；与浏览器自带的离线保存性质一致 |
| B5. 用户选中的片段 / 句子连同来源 URL 一起收藏 | v1 不做。它是学习功能（类生词本的上下文），需要单独评估引用长度与存储位置，见 Out of Scope |

### C. 保存的 URL 怎么处理

保存场景与 ADR-010 Decision 8 / ADR-026 的场景**目标相反**：那两处 URL 是给**开发者诊断用**的，所以强脱敏、丢 query 都无所谓；这里 URL 是给**用户重新打开页面用**的，必须还能打开。

| 方案 | 结论 |
| --- | --- |
| C1. 原样保存 | 否决。fragment 与跟踪参数没有价值，还平白多存东西 |
| C2. 同 `page_reports` 的强脱敏（只留 origin + path，路径里的疑似标识符换成 `:redacted`） | **否决。** 很多站点靠 query 定位文章（`?id=123`、`?p=456`），砍掉就打不开；`:redacted` 的路径段更打不开。功能性优先 |
| **C3.（采用）去掉 fragment 和已知跟踪参数（`utm_*`、`fbclid`、`gclid`、`mc_*`；X 分享链接里的 `s`、`t`），其余 query 原样保留；只接受 http(s)** | 保留可重新打开所需的一切，去掉纯噪声。残余风险（query 里带会话令牌的链接）由「用户主动保存 + 保存前展示 + 随时可删」承担，见 Decision 4 |

### D. 「用户主动上报问题」与「用户主动保存」要不要走同一条路径

用户提出：两者都是「用户主动提交的页面」，可以走同一路径，多一个字段区分「这是异常上报」。

| 方案 | 结论 |
| --- | --- |
| D1. 合成一张表，加 `kind` 列（`saved` / `issue_report`） | 评估后**否决**，理由是两者的生命周期与可见性根本不同：<br>• **可见性**：收藏出现在用户自己的列表里；上报是给开发者看的，不应出现在用户列表。<br>• **保留期**：收藏保留到用户删除；上报 90 天自动清理。<br>• **上限**：收藏上限高且**超限拒绝、不静默淘汰**（这是用户的数据）；上报每人 50 条、淘汰最旧。<br>• **URL 处理**：收藏要保功能（Options C3），上报要强脱敏。<br>合表意味着每一条查询、导出、删除、清理都必须记得按 `kind` 过滤。**最坏的一种漏写**：现有的 90 天清理任务（`pagereport.PurgeExpired`，按 `created_at` 删除）如果作用在合并后的表上而漏了 `kind` 条件，会**把用户的收藏在 90 天后静默删光**。分表让这类错误在结构上不可能发生 |
| **D2.（采用）分表：`page_reports`（已实现）与新的 `saved_pages`；共享代码，不共享存储** | 用户想要的「同一条路径」在**交互与代码**层面实现：同样的「用户点击 → 显示将发送的内容 → 确认」形态、同一个 URL 规范化包（两个 profile：`ForReport` 强脱敏 / `ForSave` 保功能）、扩展里同一个提示组件。存储与生命周期保持分开 |

### E. 热度榜 / 内容推荐要不要靠被动采集

| 方案 | 结论 |
| --- | --- |
| E1. 被动汇总所有用户读了什么，做「大家都在读」 | **否决**（同 A1 的三条理由） |
| E2. 基于**显式收藏**的计数：收藏时另有独立选项「允许匿名计入热门」，**默认关闭**；榜单只展示被至少 N 个不同用户（N 暂定 5–10）收藏的文章，避免暴露个人的私人链接 | **预留，v1 不做。** 需要另立 ADR；`saved_pages` 加一列 `discoverable BOOLEAN DEFAULT 0` 即可，不需要迁移工具 |
| **E3.（v1 的推荐方向）精选文章库 + 按用户自己的词汇量个性化** | 服务端已经有每个用户的词汇与查词数据，可以推荐「适合你水平的文章」。这对英语学习产品比「别人在读什么」更有价值，且完全不涉及任何人的浏览记录 |

**规模现实**：用户是个位数到几百时，「很多人都在读」的信号没有统计意义，几十人的数据撑不起榜单。热度榜在用户上到几千之后才值得做（Revisit Trigger）。

## Decision

### 1. 默认不记录阅读历史

服务端零历史（继承 ADR-028 Decision 3/4 的立场）。隐私政策与服务条款照此表述（隐私页现有措辞已经如此，见 Decision 8）。

### 2. 本地阅读历史（如做）只存本机

若将来要给用户一个「我读过什么」的列表：桌面存 `chrome.storage.local`，移动端存本地数据库，**永不上传**，用户可一键清除。**v1 不强制做，且不预先在任何条款里声明**（见 Rationale「为什么现在不加前瞻性条款」）；真做的时候，隐私政策同步加一句说明「这份记录只在你的设备上」。

### 3. 保存文章：URL + 标题，不存正文、不存译文

- 表 `saved_pages`：`id`、`user_id`、`url`（按 Options C3 规范化）、`title`（≤200 字，超出截断）、`host`、`created_at`。
- **服务端不主动抓取任何 URL**：标题由扩展 / 移动端在用户的页面上取得后提交。这同时避开了「服务端代抓」带来的站点条款、抓取合规与 SSRF 风险。
- 端点：`POST /api/saved-pages`、`GET /api/saved-pages`、`PATCH /api/saved-pages/:id`（改标题或 URL；URL 改后重新规范化，若与该用户已有的另一条重复则返回 409）、`DELETE /api/saved-pages/:id`、`DELETE /api/saved-pages`（全部删除）、导出。均不在计量路径上。
- **上限**：每人 1000 条，标题 ≤200 字（2026-09-20 确认采用默认值）。**超限时拒绝并明确提示，不静默淘汰旧的**——这是用户的数据，不是诊断日志。
- **保留：永久，没有自动过期**，直到用户删除或账号删除。这与 `page_reports`（90 天自动清理）是刻意的对照。**账号删除必须级联清理**（硬前置，见关联清单）。
- **只有本人能看：服务端不提供任何管理员查看收藏的入口**（对比 `page_reports`，那个是给管理员看的）。所有读写都带 `user_id` 条件。注意这是访问控制而不是加密——能读数据库的人在技术上仍然读得到，所以隐私政策的措辞是「我们的应用不提供任何人浏览你的收藏列表的界面」这一类**事实陈述**，**不能**写成「技术上无法访问」。
- 同一用户重复保存同一规范化 URL：视为已保存，不新增一行。

### 4. 保存的交互：显式、逐次、看得见；管理都在 enx-ui

- 扩展 popup 加「Save this page」按钮；点击后显示**将要保存的 URL 与标题**，确认后才发送。没有任何被动保存。
- 提示文案说明「链接里的参数会一并保存」，因为 Options C3 保留了 query。
- 移动端通过系统分享菜单把链接交给 App，同样是用户的显式动作。
- **enx-ui 的 Saved 页是用户读写自己这份数据的界面**：查看列表、编辑标题与 URL、删除单条、清空全部、导出。它与扩展 / 移动端调用同一组端点，不另开后门。

### 5. 移动端如何阅读一篇已保存的文章

服务端从不持有正文。移动端用 App 内 WebView、以**用户自己的登录态**加载该 URL，在**设备上**抽取文本，之后的查词 / 划词翻译沿用现有接口（只发单词与选中的句子）。付费墙站点（白名单里有 NYTimes、Reuters 等）因此天然只有订阅用户能读到全文，而这正是它应有的样子。需要离线阅读时用 Options B4（设备本地缓存）。

### 6. 与问题上报的关系

按 Options D2：`page_reports` 保持现状不动；抽出 `urlnorm` 包，服务端与扩展各提供 `ForReport`（现有的强脱敏）与 `ForSave`（去 fragment + 跟踪参数）两个 profile。两边的用例继续镜像（服务端 Go 测试与扩展 Jest 测试同一批 case），防止漂移。

### 7. 热度与推荐

v1 不做基于用户行为的热度榜；推荐走 Options E3（精选库 + 个性化）。若将来做热度榜，只用 `discoverable` 显式同意的收藏，并设最小人数阈值，另立 ADR。

### 8. 上线前的文案与合规清单（硬前置）

**隐私政策（`enx-ui/src/app/privacy/page.tsx` 与 `zh/privacy/page.tsx`，中英同步）**：
- 「离开你的浏览器的内容」列表新增「你主动保存的页面地址与标题」。
- 数据表新增一行：保存的页面 / 用途（跨设备继续阅读）/ 保留到你删除或账号删除。
- 「我们刻意不保存什么」一节的例外列表现为两项：你主动发送的问题报告（ADR-010 Decision 8）、你主动保存的页面（本 ADR）。**其余仍然不存**：任何你没有主动交给我们的页面地址、页面正文、译文、阅读时刻。
- 明确写：**浏览历史不会被上传**；若存在本地阅读记录，它只在你的设备上。

**服务条款**：说明保存的页面可随时删除、账号删除时一并删除；说明我们不保存被保存文章的正文，重新打开页面依赖原站点仍然可访问。

**Chrome 应用商店**：「保存」是用户点击触发、按钮旁即披露将保存什么的功能，满足「界面内披露 + 明确的同意动作」；商店页描述里要写明这个功能。

**律师确认（我无法代替）**：运营主体在大陆，用户的收藏列表属于个人信息，需要明确同意、删除权、导出权；上线前请就 URL + 标题的存储与文案做一次确认。

## Rationale

### 为什么不存正文（以及译文）

以下是工程侧的风险梳理，**不是法律意见**：

- **复制与翻译是两项独立的专有权利。** 服务端保存一篇文章的全文是复制；保存它的中文译文还是翻译 / 改编。「用户为个人学习而使用」的合理使用，保护的主要是**用户**，并不自动覆盖「替用户保存副本的平台」。
- **避风港规则不是万能的。** 各法域的避风港（如中国的信息存储空间服务规则、美国的 DMCA 512(c)）以「通知—删除」流程等条件为前提，且主要为「对外提供」设计；纯私人存储处于灰色地带。做全文存储的稍后读产品有，但它们有专门的法务与投诉处理流程，我们没有。
- **白名单站点风险最高。** 白名单里有 NYTimes、Reuters 等付费墙、且对版权很积极的媒体。存它们的全文，等于在我们的服务器上保存付费墙后面的内容。
- **站点自己的条款。** 许多站点（包括 X）的条款禁止抓取与转存；服务端代抓最糟，由用户浏览器提交也仍是复制。
- **收益很小。** 移动端本来就要用用户自己的登录态去打开页面（Decision 5），服务端快照对付费墙页面拿不到，对公开页面则只多了一份「链接失效后仍能读」的便利。

存 URL + 标题的风险面小得多：URL 本身不受著作权保护，标题是一句话的题名，这也是稍后读类产品的最小元数据。风险不是零，所以 Decision 8 仍要求律师确认。

### 为什么这与 Reader（ADR-022）不矛盾

Reader 存的是用户**自己粘贴**的文本，7 天过期、50 篇上限。那是用户自己提供的内容，且保留期短；本 ADR 拒绝的是「我们替用户从别人的站点上取正文并长期保存」。两者的差别正是「谁把内容带进来的、留多久」。

### 为什么现在不加「未来可能在本地保存阅读历史」的前瞻性条款

- 隐私政策写的是**当前实际做的事**。「我们将来可能……」这类泛泛的预告既不是真实的披露，也会被读成一张宽泛的授权，与产品「我们不记录你读的是什么」的表态互相拉扯。
- 本地历史**从不离开用户的设备**，我们不收集、不处理它，所以它本来就不需要用户对我们「同意」什么；真做的时候补一句说明即可。
- 如果这个功能最终没做，就什么都不用改；条款里预告一个不存在的功能，反而要再改回来。
- 通常，隐私政策的实质性变更要**通知**用户，而不一定要重新征得同意；需要用户明确同意的，是新增的、以同意为依据的数据处理。本项目自己的隐私页已经承诺「对你有实质影响的变更，会在生效前通过邮件通知你」（这是对自己的约束，做保存功能时要兑现）。保存功能的「同意」，就是用户在界面里看到将保存什么之后的那一次点击（Decision 4）。这是工程侧的理解，仍归入 Decision 8 的律师确认范围。

### 为什么不静默淘汰、要求账号删除

收藏是用户的数据，不是我们的诊断日志：达到上限时让用户知道并自己决定删哪条，比悄悄丢掉最旧的一条更符合「保存」这个动词的含义。账号删除同理——服务端持有了一份属于用户的东西，就有义务在用户离开时删掉。

---

## Consequences

### Positive

- 「默认不记录」的承诺继续成立，对外表述简单且真实；例外只有两个，都是用户点击触发。
- 服务端始终没有第三方文章的正文，版权与站点条款风险面很小。
- 与现有交互（问题上报的确认提示）形态一致，扩展里复用同一个组件。

### Negative

- 链接失效（link rot）后收藏就打不开了，没有快照兜底。
- 移动端阅读依赖原站点可访问、且需要用户在 WebView 里有登录态（X、付费墙媒体都要登录）。
- 保存 query 意味着带令牌的链接也会被存，只能靠「主动保存 + 展示 + 可删」缓解。
- 需要新表、五个端点、账号删除、导出，工作量不小。

### Mitigation

- 移动端用设备本地缓存（Options B4）解决离线，不碰服务端。
- 保存确认区展示完整 URL，用户一眼可见是否带了参数。

---

## Out of Scope（本次不做）

- 服务端正文快照、译文存储、全文搜索（都依赖存正文）。
- 收藏「片段 / 句子 + 来源 URL」（Options B5）。
- 热度榜与 `discoverable` 同意流程（Options E2）。
- 被动阅读历史的任何上传，包括 opt-in（Options A2）。
- 标签、文件夹、分享给他人、浏览器端导入书签。

---

## Revisit Trigger

- **用户量上到几千**：评估热度榜，走 Options E2，另立 ADR。
- **用户强烈要求离线、跨设备的正文**：先用设备本地缓存（B4）；只有在**取得律师意见并逐站点评估**后，才考虑服务端快照，且不含译文。
- **律师认为 URL + 标题的存储也需要额外同意或告知**：改为「仅本地保存，不同步」，跨设备靠用户自己在手机上重新分享。
- **Chrome 应用商店政策变化**：重新核对「界面内披露 + 明确同意」对保存按钮的要求。
- **合并 `page_reports` 与 `saved_pages` 的诉求再次出现**：先回答 Options D1 的最坏情形（清理任务误删收藏）如何在结构上被防住，再谈合表。
