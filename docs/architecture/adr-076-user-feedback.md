# ADR-076：用户反馈系统：各种反馈渠道统一成一类记录，关联用户账号，不自动过期

现在用户把问题交给我们的渠道各自一套：页面上报（ADR-010）有自己的表、90 天过期、每人 50 条；释义反馈（ADR-026）设计了另一张表，还没实现；回传正文选择（ADR-073 决定 5）又打算单独建一张不存账号的表。用户也没有地方随手写一句「这里有问题」。

本 ADR 建一个**用户反馈**系统：所有渠道都是它的一种**反馈类型**，存进同一张表、在同一个管理页里看。产品还没正式上线，现在统一，迁移成本最低。

## 决定 1：一个概念，多种类型

**用户反馈（feedback）** 是用户交给维护者的一条记录，用来发现和处理问题。第一版有四种类型：

| 类型 | 谁触发 | 内容 |
| --- | --- | --- |
| 文字反馈（`text`） | 用户在入口里写一段话并发送 | 用户写的描述 + 页面地址 + 场景信息 |
| 页面上报（`page_report`） | 学习模式处理失败后，用户点「Send report」（ADR-010 决定 6–7） | 页面地址 + 失败原因 + adapter |
| 正文选择（`article_choice`） | 用户同意回传后，每次确认一次正文选择（ADR-073） | 页面地址 + 生成的 selector + 自动识别当时的结果 |
| 释义反馈（`definition`） | 单词卡上的「报告释义问题」（ADR-026，仍排在后面实现） | ADR-026 决定 2、5 的字段和快照 |

**存储：** 一张 `feedback` 表。公共列是 id、`user_id`、类型、页面地址、host、用户写的文字、场景信息、状态、创建时间；各类型自己的字段放在一个 JSON 列里。`page_reports` 的已有数据迁进来，类型记为 `page_report`，然后删掉旧表。ADR-026 的 `word_feedback` 表不再建。

**为什么合表：** ADR-010 当初不让页面上报和收藏合表，理由是两者的可见性和保留期不同，按时间清理时容易误删收藏。这次的四种类型都属于维护者、都不过期、可见性相同，那个理由不成立。合表之后，管理员在一个地方看所有问题，限额也只需要算一处。

## 决定 2：关联用户账号

每条反馈都存 `user_id`（本地用户 id），包括正文选择。

- 维护者处理问题时要能找到人：在管理页点进 ADR-049 的用户详情，必要时手动发邮件联系。
- 限额按用户算（决定 5）。
- 用户注销时，按 `user_id` 删除他的全部反馈（ADR-062）。

这修订了 ADR-073 决定 5「回传的记录不和用户账号关联」。那条的本意是把回传的记录弄得不像浏览记录；但回传本来就要用户先同意，而且不存账号就没法限额，也没法在注销时删除。

## 决定 3：页面地址只保留 origin + path，用户发送前能看到

所有类型用同一套清洗规则，就是 ADR-010 决定 8 那一套：只保留 origin + path；去掉查询参数、片段、用户名和密码；路径里像令牌、邮箱或 UUID 的段替换成 `:redacted`。扩展、enx-ui 和 enx-api 各实现一份，**服务端以自己清洗的结果为准**。

- **文字反馈：** 发送前把清洗后的地址显示在文本框下面，用户可以改，也可以删掉。服务端仍然再清洗一次。
- **页面上报：** 照旧，发送前逐字显示地址（ADR-010 决定 7）。
- **正文选择：** 用户在同意时已经知道会发送页面地址（决定 6），之后每次不再显示。
- **enx-ui 里的文字反馈：** 地址是 enx-ui 自己的页面路由。

查询参数一律不存：里面常有登录令牌、分享密钥和追踪参数，维护者处理问题也用不到。

## 决定 4：场景信息自动附带，不带页面内容

每条反馈都会附带发送时的场景信息：扩展版本（或 enx-ui 版本）、浏览器、学习模式是否开启、当前 adapter、正文来自自动识别还是用户的选择。

**不附带的：** 页面正文、页面标题、截图。释义反馈的原句是例外，因为用户报的就是这一句，ADR-026 已经定了这一点。截图第一版不做。

## 决定 5：限额：每个用户每天 50 条，可配置

- 每个用户每天最多 50 条，所有类型合计。配置项是 `FEEDBACK_DAILY_LIMIT`，默认 50。超出时返回 429，提示用户明天再发。
- 请求限流照常走 ADR-060，不另做。
- **去重：** 同一用户对同一 host 的同一个 selector，正文选择只记一条；同一页面、同一原因的页面上报 24 小时内只记一条（ADR-010 决定 9）。重复提交返回成功，不新增记录，也不占限额。
- 文字反馈的正文长度有上限（建议 2000 字符）。

这个上限是用来防止有人恶意刷爆数据库的，正常用户碰不到。

## 决定 6：正文选择回传：第一次选正文时问一次

- 默认关闭。用户**第一次开始选正文时**，问一次要不要把选择分享给我们，用来改进识别。不论同意还是拒绝，之后都不再问。
- 扩展设置页可以随时打开或关闭。
- 关掉之后就不再发送。已发送的记录保留，用户注销时一起删除。设置里的说明文字要讲清楚这一点。

这修订了 ADR-073 决定 5 的「用户第一次完成选择后问一次」：在开始选之前问，用户还没投入操作，更容易认真回答。

## 决定 7：不自动过期，管理员手动处理

- **不设保留期，不自动删除。** ADR-010 决定 9 的 90 天过期和每人 50 条上限一并取消，`runPageReportCleanup` 删掉。反馈是待处理的问题，不能在维护者看到之前就消失。
- **状态：** 每条反馈有两个状态，`new` 和 `resolved`。管理员看完、处理完就标记 `resolved`。不做更细的状态流转。
- **不自动通知用户。** 系统不发「问题已解决」邮件，需要时维护者手动联系用户。这一条和 ADR-026 决定 9 一样。
- **新反馈的邮件提醒：** 保留 ADR-010 决定 12 的 Resend 邮件提醒管理员，只针对用户主动提交的类型（文字反馈、页面上报、释义反馈）。正文选择不发提醒，否则数量太多。

## 决定 8：入口和管理页

- **扩展：** 工具栏弹窗里加「Send feedback」入口。
- **enx-ui：** 用户菜单里加「Send feedback」。
- **管理页：** 一个 `/admin/feedback` 页面，按类型和状态筛选。现有的 `/admin/page-reports` 并进来。正文选择按「host + selector」分组，显示次数和一条示例路径，供 #710 的规则候选使用。**没有任何反馈会自动变成规则、自动改词典。**
- 旧接口 `POST /api/page-reports` 保留到下一个扩展版本发布，改为写入新表；之后删除。

## 隐私前置条件

上线前，enx-ui 的隐私政策页（`/privacy`、`/zh/privacy`）要写清楚：反馈会记录什么、关联账号、不自动删除、注销时删除、正文选择默认关闭。Chrome Web Store 的数据使用披露也要同步更新。

## 没选的方案

- **各类型各自建表**（现状）：每加一种渠道就多一套限额、清理和管理页，管理员要在几个页面之间来回看。
- **正文选择不存账号**（ADR-073 原方案）：没法限额，注销时也没法删。
- **保留完整 URL**：查询参数里的令牌一旦进库，就等于我们替用户保管了别人的访问凭证。
- **只做文字反馈、不附带页面地址**：维护者大多数时候需要打开那个页面，才能复现问题。
