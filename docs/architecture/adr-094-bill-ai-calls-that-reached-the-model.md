# ADR-094：只要真实调用了模型就按 token 扣费，调用失败也扣；失败在日志里醒目标记，由管理员手动补偿

到目前为止，按 token 计费的 AI 功能都是**失败不扣费**：模型调用失败、回复解析失败或内容不合格，都返回错误，不结算（ADR-012 Decision 8、ADR-014 的 `billedCall`、ADR-045「计费细化」）。这样一来，这部分 token 成本由我们承担；而且有人可以用脚本构造让模型回复不可用的请求，反复消耗模型额度却不付费。所有者决定（2026-11-25）：**只要我们的系统真实调用了模型，就按实际 token 扣费，结果不可用也扣**。用户因此多付的积分，由管理员在巡检日志时发现并手动补偿。

## 决策

### 1. 扣费边界：模型返回了用量就扣

- **模型返回了 token 用量**：按实际 prompt / completion token 结算（`Settle`，公式和价格不变）。之后的解析失败、校验失败、内容不合格（包括 ADR-045 的不合格回复）都照样扣费。
- **调用模型之前就失败**：不扣费。包括功能未配置、未定价、余额读取失败、余额不足（402）、试用限额，以及请求参数校验失败。
- **模型本身报错或超时，拿不到用量**：不扣费。这类错误是 P0 运维问题，由运维直接处理，不靠用户付费来防范。

### 2. 用户看到的结果不变

失败仍然返回错误（502 等），不返回半成品，沿用「no silent empty result」惯例。只是余额照样扣减。

### 3. 失败要在日志里醒目标记

每一次**扣了费但没有给用户可用结果**的调用，都写一条 Error 级结构化日志，用固定的事件名，并带上 feature、user、prompt / completion token 数、扣了多少积分和失败原因，让巡检可以按事件名直接筛出来，并据此算出补偿金额。模型报错、不扣费的失败用另一个固定事件名，供运维告警。两个事件名和字段由实现 issue 定。

日志里的积分数是按 token 算出、交给 `Settle` 的应扣数。账本实际扣的可能更少：纯试用账户超出试用余额的部分会注销（ADR-048 Decision 4），结算写入失败时则一分未扣。算补偿金额时以账本的 `SETTLE` 流水为准。

### 4. 补偿由管理员手动做

不自动退款，也不自动补偿。管理员巡检时按第 3 条的日志找出受影响的用户，用 ADR-049 的管理员赠送（`GRANT_ADMIN`，`reason` 写明原因）发放补偿积分。

### 5. 结算写入失败的处理不变

模型调用成功、结算写入失败时，用户照常拿到结果，只记日志，与现状一致。

## 考虑过的方案

- **维持失败不扣费**：用户体验最直接，但 token 成本我们承担，还可以被脚本利用，免费消耗模型额度。否决。
- **失败自动退款**：等同于失败不扣费，同样会被刷，只是多了一步流水。否决。
- **模型报错时按最低 1 积分扣**：拿不到用量时没有计价依据，而且这类错误本身已是 P0 问题。否决。

## 后果

- ADR-012 Decision 8 与其他「失败路径不扣费」的说法、ADR-014 中 `billedCall` 的「A failed provider call is never charged」、ADR-045「计费细化」中「不合格的内容也不扣费」，都以本 ADR 为准。
- 实现要让各功能在解析失败时把 token 用量交回调用方。`wordcontext`、`worddef` 已经做到；`rephrase.Call` 在解析失败时会丢掉用量，需要改。现在锁定「失败不扣费」的测试（如 `TestWordInContextHandlerTranslatorErrorNotBilled`）要改成新规则。
- 解析器把不合格回复误当成功的 bug（如 #1136）比报错更糟：用户拿到错误的结果，日志里记的是成功，巡检发现不了，也就不会补偿。
- 用户可能在补偿到账之前看到余额减少。所有者接受这个代价。

## 修订记录

- 2026-11-26（#1146）：决策第 3 条补充日志中积分数的含义（应扣数，实扣以 `SETTLE` 流水为准）。原因：纯试用超额注销（ADR-048）或结算写入失败时两者不同，按日志数补偿会多发。
