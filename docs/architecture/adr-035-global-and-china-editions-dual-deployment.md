## Context

目前只有一个生产部署：AWS 东京（ADR-031），Clerk 登录（Google / GitHub），Stripe 收款，Bedrock 上的 Claude 做 AI，Chrome Web Store 分发扩展，运营主体是**个人**。

这套组合对大陆用户基本不可用，而且每一项都有结构性原因，不是体验问题：

| 依赖 | 对大陆用户的问题 |
|---|---|
| Google / GitHub 登录 | Google 打不开；GitHub 不稳定；大陆用户的主力身份是微信 / 手机号 |
| 微信登录 | 微信开放平台「网站应用」要求**已 ICP 备案的 HTTPS 域名**，且开发者资质认证**只接受企业**（个人不能认证）。ICP 备案要求服务器在大陆 —— 东京机器上的域名备不了 |
| Clerk | 美国 SaaS。大陆用户的身份数据（手机号、unionid）存进去 = 个人信息出境（PIPL 第 38 条），且访问稳定性无保证 |
| Stripe | 不收大陆主体，大陆用户也不用信用卡付订阅 |
| Chrome Web Store | 大陆网络通常打不开，用户装不了扩展 |
| 数据在东京 | 大陆用户越多，越逼近 `LAUNCH-CHECKLIST` 6.2c 的出境豁免线 |

作者在大陆**有企业主体**（海外版继续用个人主体）。这让国内合规路径第一次变得可行。

## Decision

### 1. 两个版本：海外版（global）与国内版（cn）

**同一个代码仓库、同一套镜像，部署两次**：

- **海外版**：即现在的 Catglish 生产（ADR-031），个人主体，不变。
- **国内版**：部署在大陆云上，企业主体，面向大陆用户。

不 fork 代码库，不维护长期分支。版本之间的差异**只允许**以「部署配置」的形式存在（见第 3、4 条）。

### 2. 两个版本完全隔离，账号与数据不互通

- 各自独立的数据库、用户体系、身份提供方（IdP）实例、计费账本。
- 同一个人在两边是**两个互不相关的账号**。不做跨版本登录、不做数据同步、不做账号迁移工具。
- 国内版的个人信息**只存、只处理在境内**。国内版运行时不得把用户数据发往境外服务（Clerk、Stripe、Bedrock、境外日志/监控 SaaS 等）。

理由：任何「互通」都会把跨境数据流重新引进来，把第 1 条换来的合规优势抵消掉；而一个独立开发者维护跨区账号一致性的成本远大于收益。

### 3. 按部署切换的外部依赖（配置轴）

| 配置轴 | 海外版 | 国内版 | 说明 |
|---|---|---|---|
| 运营主体 / 法律页 | 个人 | 企业 | `enx-ui/src/lib/legal.ts` 的 operator、AI provider、sub-processor 列表要变成**按版本的配置**，不能只有一份常量。`legal.test.tsx` 目前断言页面里不得出现「有限公司」——那是海外版的约束，要改成只对海外版生效 |
| 身份认证 | Clerk（Google / GitHub） | 自托管 Logto（微信扫码 / 手机号） | 见 [`adr-036`](./adr-036-china-edition-authentication-logto.md) |
| 收款 | Stripe | 微信支付 / 支付宝 | 另起 ADR；ADR-009 的积分 / 订阅领域模型（键在本地 `users.Id`）原则上复用，只换支付通道 |
| AI provider | Bedrock（Claude） | **已完成大模型备案**的国内模型 API（如 DeepSeek / Kimi / MiniMax） | `aitranslate/` 已有这几个 provider 的实现，本来就是给境内部署留的 |
| 托管 | AWS 东京 EC2 | 大陆云（选型待定：阿里云 / 腾讯云 / AWS 中国区） | 必须能办 ICP 备案 |
| CDN / DNS | Cloudflare | 大陆 CDN | Cloudflare 免费档在大陆没有节点 |
| 扩展分发 | Chrome Web Store | **Edge 加载项商店**（大陆可访问）+ 官网离线包 | 国内版扩展是独立的构建产物和独立的商店条目（不同扩展 id） |
| 前端外部资源 | — | 不得在运行时依赖大陆访问不到的第三方资源 | Google Fonts CDN、Clerk JS、Stripe.js、Google Analytics 之类 |

### 4. 切换机制：沿用现有的配置方式，不引入新机制

- **enx-api / enx-ui**：运行期配置（ADR-031 修订记录 2026-09-18 已经让镜像与环境无关）。provider 的选择是一个 env / viper 配置项，同一个二进制里包含所有 provider 的实现。
- **enx-chrome**：构建期 target（`enx-chrome/src/config/targets.ts`）。国内版加一个 target（例如 `production-cn`），产出独立的扩展包。扩展不做运行期切换 —— 两个版本的扩展 id、商店、IdP 都不同，本来就该是两个产物。
- **代码层面**：每个配置轴在代码里是一个接口（seam），具体 provider 在接口后面。新写的代码**不再直接调用** Clerk / Stripe 的 SDK，而是走这些接口 —— 这一条从现在开始生效，即使国内版还没开工。

### 5. 国内版上线的前置条件（全部满足才能对外）

资质相关，都挂在企业主体下：

1. **ICP 备案**（国内版域名，大陆服务器）+ 备案后 30 天内的**公安联网备案**。
2. **经营性 ICP 许可证**（增值电信业务经营许可证）。付费会员 / 订阅属于经营性互联网信息服务，只做非经营性备案不够。
3. **生成式 AI 合规**：国内版向公众提供 AI 翻译 / 释义 / 改写，调用的是第三方已备案大模型的 API → 走**算法备案 + 大模型登记**（省级网信办，公开资料称周期约 1–3 个月），需要准备拦截关键词库、评估测试题库、内容审核能力。⚠️ 若对模型输出做了实质性的二次加工，可能被要求改走完整的大模型备案 —— **需找律师或属地网信办确认**。另需核实 AI 生成内容标识的要求。
4. **微信开放平台**开发者资质认证（企业，年审费用约 300 元）+ 网站应用审核（要填备案号）。
5. **微信支付商户**（PC 网站 Native 支付需要已认证服务号 + 已备案域名）与**支付宝**电脑网站支付签约 —— 细节留给收款 ADR。
6. 国内版自己的隐私政策与用户协议（企业主体、境内存储、境内 sub-processor）。

### 6. 先后顺序

海外版先上线，按现有 `LAUNCH-CHECKLIST` 推进，不因本 ADR 延期。国内版在海外版稳定后启动；资质申请周期长（ICP 许可证、大模型登记都以月计），**可以提前并行申请**，不必等代码。

## Consequences

**好的**

- 国内版在备案、数据出境、收款三个问题上都走「正门」，不靠任何灰色做法（例如「国内备案机转发到东京」）。
- 海外版完全不受影响，ADR-031 不改。
- 「按配置切 provider」顺带降低了海外版自身的供应商锁定（Clerk、Stripe 都不再是散落各处的硬依赖）。

**要接受的**

- **运维翻倍**：两套部署、两套备份、两套监控、两个扩展商店条目、两套法律文本。一次发版要验证两个环境。
- **seam 改造是真实工作量**：Clerk 目前散在 enx-api 约 11 个、enx-ui 约 16 个、enx-chrome 约 14 个源文件里；Stripe 也直接嵌在 `billing/` 里。
- **功能可能分叉**：例如 GitHub 登录只有海外版有。另外很多英文站点在大陆打不开，国内版的使用重心可能更偏向粘贴文本阅读器（ADR-019）而不是网页划词 —— 这是产品问题，不在本 ADR 定。
- 资质有持续成本：年审、许可证年报、备案信息维护，以及内容审核义务。

## Alternatives considered

| 方案 | 否决理由 |
|---|---|
| 单一全球部署，给大陆用户加微信登录 | 备案要求大陆服务器，东京部署拿不到微信网站登录；数据出境问题只会越来越大 |
| 国内备案机器只接回调，转发到东京 | 规避审核，有被微信拒审或封禁的风险；数据仍然出境 |
| fork 出国内版代码库 / 长期分支 | 两份代码必然漂移；独立开发者没有维护两份代码的余力 |
| 两个版本共享账号体系 | 重新引入跨境数据流，抵消双部署的全部合规收益 |
| 海外版也迁到 AWS 中国区统一部署 | 海外用户访问中国区慢且受限；个人主体开不了中国区账号 |

## 待定（不阻塞本 ADR 被接受）

- 国内版的品牌名 / 域名（须以企业主体备案）。
- 国内版的云厂商选型。
- 国内版收款 ADR（微信支付 / 支付宝，订阅还是一次性购买积分）。
